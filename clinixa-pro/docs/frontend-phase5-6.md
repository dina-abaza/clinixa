# Frontend Notes — After Phase 5 and Phase 6

## 1. Overview

تمت إكمال البنية الأساسية للـ backend في المرحلتين الخامسة والسادسة، مع أثر مباشر على واجهة الفرونت إند. الهدف الآن هو جعل الواجهة تتعامل مع:

- استجابة API موحدة
- صلاحيات المستخدم من الـ JWT
- بيانات الإعداد الأولي والـ clinic settings
- حالة المزامنة وتفادي القيم المتقطعة
- تحذيرات غير منععة بدلًا من أخطاء كاملة

---

## 2. Contract response الذي يجب على الفرونت التعامل معه

### 2.1 النجاح

```json
{
  "ok": true,
  "data": { "id": "pat_123" },
  "warning": null
}
```

### 2.2 الخطأ

```json
{
  "ok": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "رسالة الخطأ بالعربية",
    "field": "phone"
  }
}
```

### 2.3 التحذير غير المانع

```json
{
  "ok": true,
  "data": { "id": "pat_123" },
  "warning": {
    "code": "DUPLICATE_PHONE",
    "message": "رقم الهاتف مسجل بالفعل لمريض آخر",
    "meta": { "existing_patient_id": "pat_001" }
  }
}
```

### متطلبات الفرونت

- لا تعتمد على `res.data` فقط؛ افحص `res.ok` أولاً.
- إذا كان `warning` موجودًا، اعرضه لكن لا تمنع العملية.
- إذا كان `error` موجودًا، أظهر رسالة مناسبة ومنفصلة عن `warning`.
- تعامل مع `field` إذا كان موجودًا لتمييز الحقل في النموذج.

## 3. Auth و RBAC

### 3.1 التحقق من الجلسة

- لا يُسمح أبداً باستقبال `employee_id` أو `branch_id` من الـ request body.
- `employee_id` و `branch_id` تُستخرج دائمًا من الـ token.
- كل طلبات العمليات الحساسة تحتاج middleware صلاحية مناسبة.

### 3.2 ما يحتاجه الفرونت

- حفظ الـ JWT في local storage أو session store بعد تسجيل الدخول.
- إرسال الـ token في رأس `Authorization: Bearer ...`.
- إذا أراد المستخدم الوصول إلى زر أو صفحة معينة، التحقق من صلاحية المستخدم قبل إظهارها.
- عند انتهاء الجلسة أو رفض الصلاحية، إعادة توجيه المستخدم إلى شاشة login.

### 3.3 صلاحيات مهمة

المشروع يعتمد نظام صلاحيات 17 صلاحيه، ومن المهم أن يكون الفرونت متوافقًا مع هذه القاعدة:

- سحب `view` يعني رفض بقية أفعال الموديول تلقائيًا.
- لا تعرض أزرار الإضافة/التعديل/الحذف إذا لم يمتلك المستخدم صلاحية الفعل المناسب.

## 4. Setup و initial boot

### 4.1 إعداد أول تشغيل

بعد المرحلة الخامسة، تم توحيد سير إنشاء المؤسسة أول مرة:

```json
POST /api/setup/first-run
```

الاستجابة عادةً تحتوي على:

- `token`
- `main_branch`
- بيانات clinic initial setup

### 4.2 ما يحتاجه الفرونت

- بعد التنفيذ الناجح، احفظ الـ token في حالة التطبيق.
- خزّن بيانات الفرع الأساسي في store/Context.
- إذا عادت `clinic_settings` أو `branches` فارغة، يجري إعادة توجيه إلى شاشة التهيئة.

## 5. Business rules التي تؤثر على الواجهة

### 5.1 `due` للمريض

- لا يتم تخزين `due` فعليًا في جدول المرضى.
- `due` يتم احتسابه لحظياً كحاصل:

```text
SUM(charges.amount) - SUM(payments.amount)
```

### 5.2 الحضور

- جدول attendance هو append-only.
- لا يتم حذف السجلات.
- التعديل المسموح فقط هو تغيير `status` كأن يكون:
  - waiting
  - in_progress
  - done

### 5.3 Arabic normalization

- يتم توحيد النصوص العربية قبل الحفظ أو البحث.
- هذا مهم للواجهة لأن المستخدم قد يكتب صيغاً مشابهة مثل:
  - أ / إ / آ → ا
  - ة → ه
  - ى → ي

### 5.4 temporary password

- كلمة المرور المؤقتة تُظهر مرة واحدة فقط عند إنشاء موظف جديد.
- لا تعرضها في أي شاشة لاحقة.
- في واجهة الفرونت: خزّنها فقط في الرسالة الفورية للإنشاء، ثم امسحها من التخزين المحلي بعد أول عرض.

## 6. Sync Engine — ما يهم الفرونت

### 6.1 الحالة الحالية للـ outbox

تمت إضافة نظام `sync_outbox` في المرحلة السادسة.

### 6.2 نقاط الواجهة المهمة

#### Endpoint: `GET /api/sync/status`

```json
{
  "ok": true,
  "data": {
    "enabled": true,
    "mode": "local_server",
    "pending_count": 12,
    "last_sync_at": "2026-09-02T12:00:00.000Z"
  },
  "warning": null
}
```

#### Endpoint: `POST /api/sync/retry`

```json
{
  "ok": true,
  "data": {
    "processed_count": 3
  },
  "warning": null
}
```

### 6.3 ما يحتاجه الفرونت

- عرض badge أو indicator في لوحة الإدارة:
  - `enabled / disabled`
  - `pending_count`
  - `last_sync_at`
- إذا كانت `pending_count > 0`، اعرض تنبيه خفيف للمدير.
- إذا كانت `mode` = `none`, لا تعرض مزامنة كوظيفة نشطة.
- لا تعتمد على MongoDB في الواجهة الحالية، لأن المرحلة السادسة في هذه اللحظة هي Outbox queue locally managed فقط.

### 6.4 ملاحظة مهمة

تجربة المرحلة السادسة الحالية هي:

- إنشاء سجلات في `sync_outbox`
- عدّ الصفوف `pending`
- معالجة قائمة الانتظار محليًا
- لا يوجد مزامنة فعلية إلى MongoDB Atlas بعد في هذا المستوى الأساسي

أي واجهة تحتاج إلى التعامل مع هذه الحقيقة، وعدم الاعتماد على أن كل pending يعني “تمت المزامنة فعليًا”.

## 7. Frontend UX requirements

### 7.1 في كل صفحة حساسة

- تحقق من `ok` و `error` قبل عرض بيانات الصفحة.
- إذا كانت هناك `warning`, اعرضها بطريقة غير منفعلة لكن واضحة.
- استخدم `field` لتسليط الضوء على الحقل الذي فشل التحقق.

### 7.2 إدارة القوائم الديناميكية

- عند تحديث سجل داخل جدول مثل المرضى أو الحضور أو إعدادات العيادة، تأكد من إعادة تحميل البيانات عند الحاجة.
- إذا تم تحديث `sync_outbox`, لا تعرض للمستخدم شيئًا غير متوقع؛ فقط لوحة الإدارة هي التي تعرضه.

### 7.3 حالة المزامنة في لوحة الإدارة

يجب أن يظهر في لوحة الإدارة ما يلي:

- إذا كانت المزامنة مفعلة
- عدد الصفوف المعلقة
- آخر وقت نجاح مزامنة
- إمكانية إعادة المحاولة يدويًا

## 8. Recommended frontend checklist

قبل الانتقال إلى المرحلة التالية، على الفرونت أن يكون جاهزًا لـ:

- [ ] التعامل مع `ok/error/warning` الموحد
- [ ] حفظ JWT والـ branch بشكل صحيح
- [ ] عرض/إخفاء الأزرار حسب صلاحيات المستخدم
- [ ] التعامل مع قائمة `sync_outbox` في لوحة الإدارة
- [ ] عدم الاعتماد على `due` المخزن في قاعدة المرضى
- [ ] التعامل مع البيانات العربية بشكل صحيح بعد normalization
- [ ] التعامل مع `temporary_password` كقيمة لمرة واحدة فقط

---

## 9. Final note

المرحلة الخامسة والسادسة وضعت الأساس للتعامل الآمن مع:

- المصادقة
- الصلاحيات
- الإعداد الأولي
- الـ API contract
- نظام المزامنة الأولي

وبالتالي فإن الفرونت حالياً يحتاج فقط إلى الالتزام بنموذج الاستجابة الموحد وتطبيق المنطق الخاص بالعرض فقط، دون محاولة التلاعب بقاعدة البيانات أو تجاوز الـ RBAC.
